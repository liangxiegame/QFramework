QFramework 本身支持依赖倒置原则，就是所有的模块访问和交互都可以通过接口来完成。

但是 GDScript 目前还不支持接口，其实接口在技术层面与全部都是抽象函数的抽象类是一样的，但是接口可以多继承，而抽象类只能单继承。

不过足够了。

依赖倒置原则的好处就是可以非常方便地替换方案。

比如我们目前使用的存储是用的 Config 的方式，如下所示:
![](https://file.liangxiegame.com/4b1d2fc0-cb7d-4ee0-9c76-1b8af651c114.png)

我之后想换成别的方案，比如 SQLite 或者 JSON + FileAccess ，一般情况下我们就直接改这个 StorageUtility ，但是换成别的方案后又要换回原来的方案，那么就得把代码又改回来或者用版本工具回滚过来，很不方便。

但是如果我们把 StorageUtility 定义成一个抽象类（接口），也就是 IStorageUtility，然后定义好统一的存储和保存的抽象函数，比如目前是 load_int 和 save_int，然后不同的实现方案分别用不同的 IStorageUtility 子类去实现，比如 SQLiteStorageUtility 或者 JSONStorageUtility 还有 ConfigFileStorageUtility。这样在整个游戏系统中，调用的部分是通过 IStorageUtility 去完成加载和存储工作，而具体的存储和加载细节方案则根据用哪个子类去注册来决定。

而替换一个存储方案或者扩展一个存储方案也会变得非常方便，不会影响其他调用存储和加载部分的代码。

这就是依赖倒置原则的好处。

如果是比较复杂且庞大的项目或者多人团队协作的项目，依赖倒置原则会发挥巨大的威力。

所有的模块注册，模块获取 等代码都是通过接口完成。

通过接口设计模块可以让我们更容易思考模块之间的交互和职责本身，而不是具体实现，在设计的时候可以减少很多的干扰。

当然面向接口的方式去做开发也有很多其他的好处，这当然是要靠大家随着使用时长慢慢去体会了。

甚至如果自己负责接口的设计，AI 也能产出更准确的代码。
