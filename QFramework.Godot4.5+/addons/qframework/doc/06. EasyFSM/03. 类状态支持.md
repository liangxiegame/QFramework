之前介绍的 EasyFSM 定义状态的写法叫做链式状态，链式状态的好处就是可以在节点初始化的地方就定义好状态并编写逻辑，适合快速开发快速修改迭代。

但是也有缺点，就是当状态变多或者一个状态的逻辑变得复杂，那么定义状态的脚本的代码就会变得特比多，尤其是初始化的代码会有很多。

这个时候使用类状态是更好的选择。

类状态其实就是大部分状态机的常见实现，就是将一个状态定义为一个类。

我们来看下基本使用。

## 基本使用

在任意场景任意节点，编写如下脚本。

``` python
extends Node2D

class_name EasyFSMClassStateExample

# 定义状态 Id
enum States
{
	Idle,
	Jump
}

# 定义状态机
var fsm:EasyFSM = EasyFSM.new()

# 定义 Idle 状态类
class IdleState extends EasyFSMState:
	
	func enter():
		print("idle state enter")
		# 可以在状态类内部访问目标对象
		# 因为会在构造的时候传进来
		# 但是 target 类型是 Object，需要转成具体的类型
		print(target as EasyFSMClassStateExample)
		
	func exit():
		print("idle state exit")
		
	func process(_delta:float):
		# 当按下数字 2 按下则跳转到 Jump 状态
		if Input.is_key_pressed(KEY_2):
			# 可以在状态类内部访问 fsm
			# 因为会在构造的时候传进来
			fsm.change_state(States.Jump)
	
	# 类状态必须覆写 enter exit process physics_process 抽象函数
	func physics_process(_delta:float): pass
	
func _ready() -> void:
	# 类状态通过 add_state 的方式添加
	# 类状态的构造需要传入 状态 Id | 目标对象 | 状态机对象
	fsm.add_state(IdleState.new(States.Idle,self,fsm))
	
	# 定义 Jump 状态
	# 类状态和链式状态可以混合使用
	fsm.state(
		States.Jump
	).on_enter(func():
		print("jump state enter")	
	).on_exit(func():
		print("jump state exit")	
	).on_process(func(_delta:float):
		# 当 数字 1 按下则跳转到 Idle 状态
		if Input.is_key_pressed(KEY_1):
			fsm.change_state(States.Idle)
	)
	
	# 设置初始状态
	fsm.start_state(States.Idle)

func _process(delta: float) -> void:
	# 驱动状态机的 process
	fsm.process(delta)
	
func _exit_tree() -> void:
	fsm.clear()
	fsm = null
	

```

## 链式状态 vs 类状态

链式状态适合在早期原型阶段或者比较简单的状态机逻辑，优点是快速开发，快速迭代，因为都是用的匿名函数，性能可能会稍差一些，但是可以几乎忽略不计。

类状态适合在中后期的生产阶段或者比较复杂的状态机逻辑，优点是帮助目标脚本分担逻辑，防止变得臃肿，性能也会快一些，但是可以几乎忽略不计。

链式状态可以满足 90% 的中小型独立游戏使用场景，等遇到不满足的情况下可以将逻辑搬移到类状态也是很容易的。
